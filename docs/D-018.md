# Holdout 2 Result and Implications (0/2 primary recall)

This is the public analysis of VeriSec Agent's second blind holdout evaluation.
It complements two other surfaces and does not replace them:

- **[HOLDOUT_2.md](HOLDOUT_2.md)** — the frozen protocol, full case list, selection
  method, and canonical group-level metrics table.
- **[DEVELOPMENT_LOG.md](../DEVELOPMENT_LOG.md) D-018** — the terse decision record
  (what was decided and why, with rejected alternatives).

The evaluation was run once, on 2026-07-22, against detector commit `0ca2df5`, and
its result is published as measured whatever it says. Detectors have not been, and
must not be, tuned against these now-burned cases.

---

## 1. Result summary

VeriSec produced **0 findings across all 8 blind cases**.

| Headline metric | Value |
| --- | --- |
| Primary finding recall | **0 / 2 (0.00)** |
| False positives (unexpected findings) | **0** |
| Cases evaluated | 8 |
| Total findings | 0 |
| Verification commands passed | 7 / 8 (one harness crash, see §1.3) |

### 1.1 Groups

The holdout is reported in three groups that answer different questions and are
never pooled into a single recall figure.

| Group | n | What it measures | Findings | Outcome |
| --- | ---: | --- | ---: | --- |
| A — same-class, primary-eligible | 2 | Recall on unseen fixes matching the detector's assumption | 0 | **0/2 recall — both missed** |
| B — same-class, removal-shape | 3 | Noise on real patches the detector cannot claim | 0 | No false positives |
| C — open-class | 3 | Behaviour on an unfiltered advisory sample | 0 | No false positives |

Primary recall is computed over Group A only. Groups B and C contribute to noise
and precision, never to recall in either direction.

### 1.2 Per-case breakdown

| Case | Group | Advisory | Result | Reason |
| --- | --- | --- | --- | --- |
| transformers | A | CVE-2025-2099 | Miss — 0 findings | Hardened pattern assigned to a variable and used via `re.split`; the rule matches neither |
| pygments | A | CVE-2026-4539 | Miss — 0 hypotheses | Rewritten regex is a bare literal in a lexer token tuple, with no `re.` call to anchor on |
| python-multipart | B | CVE-2024-24762 | Correct silence | Fix replaces the regex with `email.message.Message`; nothing for a hardening rule to observe |
| Black | B | CVE-2024-21503 | Correct silence | Fix removes `FIRST_NON_WHITESPACE_RE` in favour of `lstrip()` |
| PyMySQL | B | CVE-2024-36039 | Correct silence | Fix forbids dict parameters outright rather than hardening in place |
| Pillow | C | CVE-2026-59205 | Correct silence | Memory-safety class; no rule coverage |
| mistune | C | CVE-2026-59929 | Correct silence | XSS URL-sanitization class; no rule coverage |
| vLLM | C | CVE-2026-55514 | Correct silence | Assertion-DoS class; no rule coverage |

"Correct silence" means the detector stayed quiet where no finding was expected —
a precision-positive result. It is not the same as detection: Group A shows the
detector was also silent where it *should* have fired.

### 1.3 One case errored — it does not change the result

pygments' property-check command crashed with `KeyError: '1,36'`. VeriSec renders
verification argv with `str.format`, and the pygments config embeds the literal
regex quantifier `{1,36}`, which `str.format` reads as a replacement field. The
crash occurs in the verification step **after** the detector had already generated
its result (0 hypotheses, recorded in the case trace), so the miss above is a
genuine detection outcome, not a crash artifact. The harness bug is tracked as
[T-010](../TASK_TRACKER.md) and is unrelated to detector behaviour.

## 2. Key finding

**The two cases most likely to succeed were hand-picked to match the detector's
own assumption, and both were missed.**

Both Group A cases are textbook Regular Expression Denial of Service (ReDoS)
*pattern-delta* fixes: the vulnerable regex is rewritten in place to remove the
nested quantifier that causes catastrophic backtracking. This is exactly the shape
`py-regex-redos-hardening` is designed to detect. Neither fired.

The cause is structural. The rule anchors on a narrow surface form:

```
re.<func>(<inline dangerous pattern> ...)      func ∈ {search, match, compile,
                                                       fullmatch, findall, sub}
```

Real hardening commits routinely take other shapes:

| Real fix shape | Example in this holdout | Rule matches? |
| --- | --- | --- |
| Pattern assigned to a variable, then `re.split(var, ...)` | transformers | No — `split` not in the function set, pattern not inline |
| Regex as a literal inside a data structure (lexer token tuple) | pygments | No — no `re.` call at all |
| `re.compile` with flags on a separate line | (common; untested here) | Fragile |
| Construct removed entirely (regex deleted, API forbidden) | Group B | No pattern delta to observe — by design |

The detector does not generalize even within its own target class, because it
matches a syntax that genuine hardening commits frequently do not use.

## 3. Relation to previous insights

This result is not a surprise in isolation; it is the blind confirmation of a
pattern already documented internally.

| Prior insight | What it established | How Holdout 2 relates |
| --- | --- | --- |
| **D-015** | The promoted-CVE suite's `1.00` recall came from regex signatures matching the scored patches' *literal text*, not general detection. | Holdout 2 shows the same brittleness on cases the detectors had never seen — the signatures do not transfer. |
| **D-016** | The promoted-CVE benchmark row was relabelled from `measured` to `illustrative`, keeping its metrics visible but removing the detection-measurement implication. | Holdout 2 supplies the blind detection number that the promoted row never was: 0/2. |

D-015 was an analytical finding (reading the rules). D-016 was the honest
relabelling that followed. Holdout 2 is the empirical confirmation on unseen data.
The three are consistent and mutually reinforcing.

## 4. Implications

On the current evidence, VeriSec Agent is best described precisely:

- **A high-precision signature matcher.** Across two blind evaluations — this
  holdout and the self-history noise corpus — VeriSec produces very few false
  positives on real patches. In Holdout 2 it raised **zero** false positives on
  six real security fixes, including out-of-scope classes.
- **With weak generalization.** It reliably detects vulnerability shapes closely
  matching its rules' surface syntax, and misses fixes that address the same
  vulnerability class in a different form. Blind primary recall here is 0/2.

The direct consequence for public claims:

> **No unqualified detection-quality claim can be made** until the generalization
> gap ([T-011](../TASK_TRACKER.md)) is addressed and re-measured on fresh blind
> cases. Statements about VeriSec's detection should say *high-precision,
> low-recall signature matching on curated shapes*, which is what the evidence
> supports.

This is a constructive outcome, not a failure of the project. The result is only
visible — and citable — because the blind-holdout system was built to expose
exactly this gap between curated performance and generalization. A benchmark that
reported `1.00` while the detectors could not transfer to unseen patches would
have been the worse outcome; the holdout replaced a comfortable illusion with an
accurate, actionable measurement.

## 5. Next steps

### T-011 — Generalize detection beyond exact call-site syntax

The highest-value detector work the project has. Widen detection to reach the fix
shapes above — variables, `re.split`, `re.compile` with separated flags, regex
literals in data structures, and in-place validation/parameterization — preferring
AST and dataflow analysis in `python_semantics.py` over additional regex.

Two hard constraints:

1. **Measure only on new, unseen cases.** The Holdout 2 and pilot cases are burned.
   Re-measuring a widened rule against them would be measurement fraud
   (Invariant 1).
2. **Ship paired negative controls first.** A broader rule is a false-positive
   risk, and VeriSec's one demonstrated strength today is its precision. Every
   generalization must be accompanied by near-miss negative tests (Invariant 4).

### Holdout 3 — planned, after rule improvements

Once T-011 lands and passes its own negative controls, a third holdout — freshly
sourced, mechanically drawn, and frozen at the improved detector commit — will
measure whether generalization actually improved on cases neither the rules nor
this document have seen. Holdout 3 must not reuse any case from Holdout 2 or the
pilot.

A larger primary group is also desirable. Holdout 2's n=2 is a point observation,
too small to separate a weak detector from an unlucky draw; sourcing enough
primary-eligible cases for a meaningful denominator is itself part of the work,
and the scarcity of in-place-hardening fixes (documented in HOLDOUT_2.md) is a real
constraint on how quickly that can grow.
