# CLAUDE.md

Operating instructions for AI agents working in this repository.

**Read this file for constraints and commands. Read [AI_CONTEXT.md](AI_CONTEXT.md) for how the
system actually works** — architecture, vocabulary, and per-task file recipes. The two do not
overlap: this file is *what you may not do*, that file is *what things are*.

VeriSec Agent is a **deterministic** security patch review system. It contains no LLM calls and
depends on no model provider. You are a contributor to it, not a component of it. Never introduce a
model-provider dependency or an LLM call into `src/` without explicit human instruction.

## Commands

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"

python -m ruff check src tests     # must be clean before any commit
python -m pytest                   # 175 tests, ~10s — always run in full
```

The suite is fast enough that there is never a reason to run a subset and assume the rest passes.

End-to-end smoke check after touching the review loop:

```powershell
python -m verisec_agent review --diff examples/demo.diff --repo . --out verisec-runs/demo
```

Negative-control regression (run after **any** detector change — see Invariant 4):

```powershell
python -m verisec_agent eval --cases examples/negative_control_cases.json --out verisec-runs/nc
python -m verisec_agent gate --evaluation verisec-runs/nc/evaluation.json `
  --min-accepted-finding-rate 1.0 --max-unexpected-finding-rate 0.0 `
  --max-negative-control-violations 0
```

`verisec-runs/` is gitignored. Write all run output there, never elsewhere.

## Hard constraints

These are the invariants an agent is most likely to violate, in descending order of cost. Violating
one silently invalidates published measurements. If a request appears to require breaking one, stop
and say so rather than complying.

1. **Never tune detectors against frozen holdout cases.** `examples/holdout_cases.json` and the
   Django CVE-2023-46695 / mechanize 0.4.6 pair are frozen at detector commit `d9754d0`. They are
   permanently blocked from measured promotion in `case_promotion.py`. Reading them to explain a
   result is fine; changing a rule so they pass is measurement fraud.

2. **Never hand-edit benchmark numbers.** Every table in `README.md`, `docs/RELEASE_BENCHMARK.md`,
   and `docs/*.json` is generated by `verisec portfolio` / `dashboard`. If a number looks wrong,
   regenerate it. Editing the Markdown to match an expectation is the single worst change possible
   in this repo.

3. **Never let a case into a measured suite without the gate.** New CVE/PR cases go
   `case-audit` → `case-promote` → merge into `examples/promoted_candidate_cases.json`. Only after
   the promotion plan marks them eligible.

4. **Never ship a detector change without negative controls.** Every rule change needs both a
   positive test and a near-miss negative test. False positives are a first-class CI signal here,
   not an acceptable trade for recall.

5. **Validation coverage must stay evidence-backed.** A check is `covered` only on a matching
   scanner finding or a `VERISEC_EVIDENCE:` marker — never because a tool with the right capability
   ran. Capability identifies a *candidate*; evidence confers coverage. Do not weaken this.

6. **Verification execution stays governed.** `shell=False`, argv rendering, adapter and executable
   allowlists, timeout and output caps. Never introduce `shell=True`, never bypass `policy.py`,
   never widen `untrusted-fork-pr` to permit `pytest`, `poc-script`, or `custom`.

7. **Keep the runtime dependency-free.** `dependencies = []` in `pyproject.toml` is deliberate —
   VeriSec runs inside CI for untrusted PRs. New runtime dependencies need explicit human approval.
   Dev and scanner extras are the escape hatch.

8. **Do not overstate evidence.** The distinction between a blind holdout and a post-fix remeasure
   on already-observed cases is load-bearing and is stated carefully in `README.md`. Preserve that
   precision in anything you write. See [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md) D-002.

## House style

Match the surrounding code; the codebase is internally consistent, so imitation is usually correct.

- `from __future__ import annotations` at the top of every module.
- Modern typing: `str | None`, `dict[str, Any]`, `tuple[...]`. No `Optional`, no `Dict`.
- Keyword-only arguments (`*`) for anything with more than two parameters.
- Immutable data as frozen dataclasses in `models.py`; findings and reports are `tuple`, not `list`.
- Module-private helpers take a leading underscore (`_summarize`, `_finding_from_hypothesis`).
- Line length 100. Ruff `E,F,I,UP,B,SIM`.
- Comments state constraints and contracts, not narration. The code is already readable; do not add
  comments that restate it.

**Tests:** pytest, `tmp_path`, real files on disk, no mocking. Tests build an actual diff, run the
actual loop, and assert on the actual bundle. Preserve this — a mocked test here would be weaker
than the thing it replaces.

## Skills

Task-specific playbooks. The instructions live in **`.ai/skills/`** (tool-neutral, shared with
Cursor and Grok Build); `.claude/skills/*/SKILL.md` are dispatch stubs that point there, so there
is exactly one copy of each checklist. Invoke by name when the task matches:

| Skill | Use when |
|---|---|
| `architecture` | Changing the review loop, adding a module, altering the bundle contract |
| `coding` | Adding or modifying a detection rule or verification adapter |
| `debugging` | A finding fired wrong — false positive, false negative, or bad confidence |
| `review` | Pre-PR gate before requesting human review |
| `documentation` | Keeping the six documentation surfaces in sync |

Each is a checklist that encodes repo-specific ordering. They are not general advice.

**When editing a skill, edit `.ai/skills/<name>.md` — never the stub.** See
[.ai/README.md](.ai/README.md) for how other tools consume the same content.

## Session continuity

- **[TASK_TRACKER.md](TASK_TRACKER.md)** — what is active, blocked, and done. Read at session
  start; update at session end.
- **[DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md)** — append-only decision record. Append when you make
  a choice a future change could accidentally undo. Never rewrite prior entries.
- **[CHANGELOG.md](CHANGELOG.md)** — user-visible changes only, Keep-a-Changelog format.

The boundary matters: CHANGELOG records *what changed for users*; DEVELOPMENT_LOG records *why we
chose it*. A decision with no user-visible effect belongs only in the log. Never duplicate content
between them.

## Working agreements

- **Report failures honestly.** If tests fail, show the output. If a criterion is unmet, say
  partial. This repo's entire value is calibrated, non-inflated claims about detection quality —
  do not report your own work in a way its own gates would reject.
- **Scope tightly.** One detector family or one documentation surface per PR (`CONTRIBUTING.md`).
- **Uncommitted work exists.** Branch `cyb/release-hardening` carries substantial unlanded changes.
  Check `git status` before assuming the tree is clean.
- **Prefer semantics over regex.** New detection belongs in `python_semantics.py` (AST/dataflow)
  first; regex in `hypotheses.py` is a secondary signal only.
